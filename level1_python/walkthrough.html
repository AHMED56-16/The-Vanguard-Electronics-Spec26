03 / What is actually transmitted?

One marker, then one frame

The marker itself is not part of the 64-byte transfer frame. Our example uses a CCSDS TM primary header, a simple Virtual Channel Access (VCA) application payload, and a CCSDS frame error-control checksum. The diagram below is schematic, not drawn to byte scale.

Total on wire: 544 bits per frame group. Every following marker starts a new group. We deliberately put a 73-bit random prefix in front to show that sync detection must work at arbitrary bit positions.

What do those parts mean?

ASM: “The message starts here.” The chosen CCSDS pattern is 00011010 11001111 11111100 00011101.

Header: “Which spacecraft and virtual channel? What frame counter?”

Data: “Which sensor readings?” Our teaching example stores simple ASCII KEY=VALUE pairs inside a VCA data field.

FECF: 16-bit error-detection checksum, used to reject corrupted frames. It detects errors; it does not repair them.

Why not demand an exact 32/32 match?

At low signal quality, one or two marker bits may flip. A threshold like 28/32 accepts up to 4 incorrect marker bits.

But lowering the threshold also makes random payload data more likely to look like a marker.

05 / Turn detected bits into real meaning

Extract, check, decode, route

Suppose a marker was found at bit P. We start reading the next 512 bits at P + 32, group every 8 bits into a byte, validate the CRC, decode the header, and then interpret the application data.

Virtual channels are like numbered lanes sharing the same radio link. VC0 carries housekeeping, VC1 power, and VC2 attitude in this demo. This sensor record is deliberately easy to read; real missions define their own payload formats.

Why the check matters

  1. 1. Detect possible start: matching bits ≥ threshold. This is only a candidate.
  2. 2. Copy fixed frame: 64 bytes after the marker. The frame size must be known beforehand.
  3. 3. Validate FECF: calculate 16-bit CRC on the first 62 bytes and compare with the last 2 bytes.
  4. 4. Decode the header: spacecraft ID, VCID, master/VC frame counters, service mode.
  5. 5. Read measurements: parse the teaching payload if (and only if) the checks pass.

07 / What comes after Level 1?

This is your blueprint for Levels 2 and 3

You are not rewriting the whole project. You will implement the same pipeline using hardware logic, then prove its speed and resource usage.

LEVEL 1 • SOFTWARE MODEL

What you have now

Bit generator, BPSK + AWGN, sliding correlator, threshold decision, false-alarm measurements, frame extraction, CRC, three virtual channels and BER plots.

LEVEL 2 • VERILOG / VHDL

Replace Python operations with circuits

32-bit shift register → parallel compare → population count → threshold pulse → lock FSM → 512-bit capture → CRC → VCID demultiplexer.

LEVEL 3 • FPGA SYNTHESIS

Prove timing at ≥ 50 MHz

Target an FPGA in Vivado or similar. Add a create_clock -period 20.000 constraint. Export LUT/FF utilization and worst-path timing report; board not required.

Export test inputs for your HDL testbench

Bridge from Phase 1 → Phase 2

Download one received bit per line for Verilog $readmemb. The truth CSV tells you where markers were actually sent, so a self-checking testbench can compare your HDL output with known correct positions. These browser vectors use the current interactive settings.

Level 2: Which Verilog modules do I need?

bit_shift_32: store the newest 32 bits. asm_correlator: XNOR each input bit with the marker and add up 32 match flags. lock_fsm: SEARCH → VERIFY → LOCKED → SEARCH, using frame spacing and missed markers. frame_capture: collect 512 data bits after a valid marker. fecf_checker: compute the same CRC-16. vc_router: use 3-bit VCID to send good frame bytes to the right output. Use the downloaded bit vectors as input to a clocked testbench. Frame-spacing and false-positive handling need particular care in the FSM.

Level 2: What should the self-checking testbench verify?

Start with no noise (all markers detected, all CRCs good). Then inject 1 to 4 bit flips into a marker; test 5 flips for a threshold of 28. Insert and delete one bit inside data, verify the damaged frame fails CRC, and verify the next marker is still found. Test incorrect offsets, false marker candidates, several VCIDs, wraparound of frame counters, and acquisition / verification / loss of lock. Set a 20 ns clock period for 50 MHz and account for pipeline latency.

Level 3: What precisely do judges want to see?

Vivado (or another supported FPGA tool) synthesis reports showing LUTs, flip-flops, and the worst timing path; an explicit clock constraint meeting 50 MHz or higher; a readable block diagram; and a waveform/testbench proving the FSM and channel extraction. A physical board is optional. Timing must be confirmed in the tool, not guessed from the Python speed.

Is this a full CCSDS flight-protocol stack?

No. The 32-bit marker, TM primary header field layout, Virtual Channel Access mode and 16-bit FECF are CCSDS-based. Our data field is a small educational ASCII record, not a CCSDS Space Packet. This model omits carrier acquisition, FEC decoders, pseudo-randomizer/derandomizer, symbol-timing recovery and many mission-dependent frame options. You can clearly explain this limitation to the judges.
